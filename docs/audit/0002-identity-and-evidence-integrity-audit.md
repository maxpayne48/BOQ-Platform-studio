# Audit 0002 — Project-Identity Similarity & Evidence-Integrity Findings

Date: 2026-07-24
Scope: the five specific problems in the brief (identical-BOQ replay, 41%/50%/50% similarity, ₹310→₹1050-shaped rate substitution), re-checked against the **current** code (post ADR-0001) and against the project's own persisted stores.
Method: static trace + live data forensics. `rfqs_store.json`, `rfq_items_store.json`, `historical_boqs_store.json` already contain a real, self-referential reproduction of Problem 1 — used as ground truth instead of speculation.

**Relationship to existing docs:** `docs/audit/recommendation-pipeline-audit.md` + `docs/adr/0001-single-source-of-truth-commercial-decision.md` were already implemented today and correctly fixed a *different* failure class (5 independent re-derivations of approval/status). That work is real and holds up under inspection. **It did not touch, and could not have fixed, the defects below** — they live one layer upstream, in Stage-1 project-similarity input and in the historical-evidence selection fallback, not in the approval/interpretation layer ADR-0001 addressed.

---

## 0. The reproduction already sitting in the data

`rfqs_store.json` contains `rfq_pl2g9aiph`, `projectName: "Copy of KOHLER PUNE FS 16TH JUNE"` — a literal re-upload of historical project `hist_vsro0d05m`, `"KOHLER PUNE FS 16TH JUNE"`. This is Problem 1's exact test case, already run, already rated. Observed:

- A quarter-plus of items had recommended rates deviating **more than 5%** from the historical rate attached to their own byte-identical description match.
- Some deviations were catastrophic: `"Tile Cladding (1200mm X 1200mm) - Type 2"` — historical ₹3,500 → recommended **₹0.15**. `"Water Body flooring"` — historical ₹550,000 → recommended **₹0.15**. `"PCC - upto 75-100mm thick"` — historical ₹1,050 → recommended ₹5,500.

This is the ₹310→₹1050 pattern from the brief, reproduced at scale, with exact file/function root causes (§3).

---

## 1. Why Project Similarity reads 41% for an identical project

`src/RecommendationEngineV2.ts` (`getSimilarProjects`) is architecturally sound — a genuine weighted multi-factor score (type 30%, cost 20%, size 20%, city 20%, grade 10%); for a truly identical project every factor should hit 1.0. The bug isn't the scoring function — it's what gets fed into it.

`server.ts`, inside `POST /api/rfqs/:id/recommend`: whenever the recommend request doesn't carry explicit `projectCost`/`projectSize`/`city` and the RFQ's own `projectContext` hasn't been populated with real values, these fall back to **fixed placeholder constants**: ₹1.5 Cr, 50,000 sq ft, "Delhi NCR", "Commercial Office" — regardless of what the uploaded file actually is.

For `rfq_pl2g9aiph` (real Kohler profile: real replay-derived cost, 6,91,250 sq ft, Pune): Type match (0.30) + Grade match (0.10) + ~0 on cost/size/city = **~0.40 → the 41% in the brief**. Persisted in `rfq_items_store.json` as `projectSimilarity: 41` on multiple items.

**Root cause:** the system has no way to notice "this RFQ's own historical twin is sitting right there in the historical database" and silently substitutes a generic profile that looks nothing like the real one.

---

## 2. Why Item/Specification Similarity read ~50% for identical descriptions

They don't, at the layer that computes them. `HistoricalRetrievalEngine`'s `wordOverlapScore` correctly returns **100** for identical text (confirmed in persisted data: `scores: { semantic: 100, specification: 100, material: 100 }`). The "50%" is the downstream composite: `overallMatchScore` is a **product** (by explicit design), so `projectFrac = 0.41` from §1 multiplies a perfect 100/100/100 item match down to ~51. Fixing §1 fixes this symptom automatically — no change needed to the scoring functions.

---

## 3. Why a correct historical rate gets rejected in favor of a wrong one (the ₹310→₹1050 mechanism)

Observed live on `rfqit_li3zpt01i` ("Tile Cladding (1200mm X 1200mm) - Type 2"): `historicalCandidates` contained exactly one properly-gated candidate (Kohler, ₹3,500) — but the final evidence pool contained candidates from ungated paths, including a corrupted **₹0.15** rate, which was `selected: true`; final `recommendedRate: 0.15` with `decision.failedValidations: []`.

**Root cause A — data quality:** `"Vitrified tile - Type - 01 - 800mm x 800mm"` recorded at ₹0.165 in the master catalog — physically impossible, 4-5 orders of magnitude off neighboring rates. No rate-plausibility check existed at ingestion.

**Root cause B — ungated fallback:** `ProjectCalibrationEngine.selectHistoricalEvidence`'s else-branch falls back to `matchedMaster.historicalRates` raw — bounded only by the Stage-1 shortlist, never by the Item-Family/UOM/commercial-equivalence/plausibility gates the primary path enforces. Similarly, `ProgressiveMatchingEngine.buildCandidatesFromMasters` pooled raw rates from every project in the catalog with identical flat synthetic scores — so "selection" degenerated to array order.

**Root cause C — self-anchored guard:** `HistoricalRetrievalEngine`'s ±3x plausibility band anchors to `ranked[0].rate` — the top-scored candidate — so a noise-ranked corrupted candidate can protect itself and reject the correct evidence.

**Root cause D — quantity over quality:** the self-validation pass adopted a re-estimate whenever it had *more references* ("16 reference(s) vs. 1 previously"), letting loosely-related relaxed-tier pools displace a single exact historical match.

**Why validation didn't catch it:** the commercial-plausibility check compares the recommended rate against the selected evidence's own min/max — the corrupted number is validated against itself.

## 4. Direct answers to the brief's numbered questions

1. **Same BOQ ≠ same recommendations?** Stage-1 inputs silently defaulted (§1) + ungated evidence fallback (§3). Both deterministic, both cited to file/line.
2. **Project Similarity 41%?** §1 — fabricated default profile vs the real historical profile.
3. **Item Similarity 50%?** §2 — multiplicative composite propagating §1's broken project score; item scoring itself returns 100.
4. **Specification Similarity 50%?** Same as #3.
5. **Correct rate rejected?** §3 Root Causes A-D.
6. **Wrong rate selected?** Won the ranking inside an ungated pool (or was protected by the self-anchored guard).
7. **Where is the recommendation generated?** Unchanged from the prior audit: baseline → engineering adjustment → progressive matching → calibration → self-validation, per `server.ts`.
8. **Which code computes similarity?** Project: `RecommendationEngineV2.getSimilarProjects`. Item/spec: `HistoricalRetrievalEngine`'s `wordOverlapScore`/`numericJaccard`. Composite: `HistoricalRetrievalEngine` overallMatchScore product.
9. **Which code ranks evidence?** `HistoricalRetrievalEngine` (candidate list) and `ProjectCalibrationEngine.selectHistoricalEvidence` (selection) — §3 shows the second sometimes ran over a different, ungated pool.
10. **Does Master BOQ influence commercial recommendation?** Only as the vehicle for historical rates + engineering classification — the defect is an un-vetted corrupted value, not architectural leakage.
11. **Does fallback logic override historical evidence?** Yes — §3 Root Cause B, concretely.
12. **Duplicated engines?** No longer — ADR-0001 removed them; confirmed.
13. **Architectural violations/dead code?** `recommendationTrace.explanation` written once by the baseline stage and never regenerated on later overwrites — a trace can tell a fabricated provenance story (e.g. "₹3,500 used directly" for a ₹0.15 item). A narrower recurrence of the "5 writers" problem, unfixed by ADR-0001 (which covered approval status only).
14. **Can identical projects fail to produce identical outputs?** Yes — confirmed in this codebase's own persisted data.

---

## 5. Fixes, in severity order

1. **(Highest — silent price corruption)** Stop `selectHistoricalEvidence`'s fallback (and every other evidence pool) from bypassing gating.
2. **(High — data quality)** Rate-plausibility check at Master BOQ ingestion (median/MAD, not min/max); flag/quarantine with a trace, never silently drop.
3. **(High — root cause of 41%/50%/50%)** Recognize a re-uploaded historical project and use its real profile instead of placeholder defaults. Input-completeness fix only — no rate bypass.
4. **(Medium)** Anchor the retrieval plausibility guard to something more robust than `ranked[0]`.
5. **(Medium)** Regenerate `recommendationTrace` whenever a later stage overwrites the rate — single writer at the end, same pattern as approval status.
6. **(Low, hygiene)** Validate the selected rate against a source-independent sanity band as a second line of defense.

## Implementation Notes (2026-07-24, same day)

Fixes **1, 2, 3, and 5** were implemented as four separate commits (fix 4 — the `ranked[0]` anchor — and fix 6 were explicitly out of the requested scope and remain open; fix 4's failure mode is however substantially defused because the pool-median gate below never anchors to the top-ranked candidate).

**Regression metric.** `test_historical_replay.cjs` was rewritten first (commit `2477f34`) — the old script depended on retired fields (`matchedProjectName`, `replayDetected`, `item.status`). It joins the RFQ's items to the historical project's row mappings by sheet+row (fallback: unambiguous exact description) and counts recommended-vs-historical deviations > 5%. All numbers below are on `rfq_pl2g9aiph` ("Copy of KOHLER PUNE FS 16TH JUNE"), 539 ground-truth-matched items, recommend invoked **with an empty request body** (the exact defaulted-profile path that produced the original failure):

| State | >5% deviations | Catastrophic (>90% off) | Kohler project similarity |
|---|---|---|---|
| Baseline (post-ADR-0001, pre-fix) | **280 (51.9%)** | 94 | 41% |
| After fix 1 (evidence gating) | 239 (44.3%) | 42 | 41% |
| After fix 2 (ingestion quarantine) | 239 (44.3%) | 42 | 41% |
| After fix 3 (real twin profile) | **118 (21.9%)** | 31 | **95% (rank #1)** |
| After fix 5/trace fix | 118 (21.9%) | 31 | 95% |

**Fix 1 (commit `4d32c03`) — every evidence pool gated.** (a) `ProjectCalibrationEngine.filterHistoricalEvidence` gained an "Implausible Rate" rejection: order-of-magnitude outliers (5x ratio band) against the **median of the candidate pool itself** (≥3 observations) — applied uniformly to primary candidates, the matched-master fallback branch, and relaxed-tier pools, and anchored to the pool median so a corrupted value can never protect itself by out-ranking the guard. The fallback branch's item-family/UOM/equivalence gates are inherently satisfied there (the pool is the same matched master's own sibling rates) — documented in place. (b) `ProgressiveMatchingEngine.buildCandidatesFromMasters` now hard-excludes projects outside the Stage-1 shortlist and scales the synthetic tier score by the originating project's Stage-1 similarity — previously all tier candidates carried an identical flat score, so selection degenerated to array order (how ₹0.15 beat ₹2,646-₹4,000). (c) Root Cause D: the self-validation adoption rule compares evidence **quality** (`selectedMatchScore`) instead of pool size; reference count is only the tiebreak. Wrong-item substitutions (fire extinguisher ₹480 → ₹36,000 class) were eliminated by this commit.

**Fix 2 (commit `c84f99b`) — ingestion quarantine.** `precomputeMasterItemFields` vets `historicalRates` before any stats are derived: a rate 10x off the median of its own siblings AND ≥6 MAD-based robust z-scores outside the item's own dispersion is moved to a new auditable `MasterBOQItem.quarantinedRates` field (reason + project, console-logged) and removed from all parallel occurrence arrays. A one-time vetting migration triggers off the marker's absence. On the current store it quarantined exactly 4 rates (e.g. ₹96,070 "40mm dia." vs sibling median ₹3,046). The MAD guard deliberately protects legitimately wide spreads — e.g. ambiguous "150 NB" masters pooling a real ₹90 Kohler rate with ₹3-5k cross-project scopes are NOT quarantined. **Residual data debt:** masters whose *every* sibling is corrupted (`"Vitrified tile - Type - 01"` at [0.15, 0.18]) are undetectable by intra-item comparison; they stay guarded only by fix 1's pool gate, and would need a domain-level sanity band (audit fix 6) to be caught at source.

**Fix 3 (commit `afc6309`) — real profile for a recognized re-upload.** The recommend route normalizes the RFQ's projectName/fileName (strips "copy of", extensions, punctuation) and matches it against `historicalBOQs`. On a match, the historical record's real profile (actual cost via `getHistoricalProjectCost`, real size/city/type) fills any parameter the request didn't provide. Precedence: explicit request body > identified twin > RFQ's own `projectContext` (deliberately below the twin — projectContext is overwritten with whatever profile a previous run used, so after one defaulted run it holds exactly the fabricated values) > placeholder default. No rate bypass, no exact-match branch — Stage-1 and all downstream stages run unchanged on better inputs. Kohler similarity went 41% → 95% and the deviation count halved.

**Fix 5 (commit `0b020a1`) — trace reconciliation.** `CommercialDecisionEngine.finalizeItemDecision` now reconciles `recommendationTrace` exactly once, at the end (same single-writer pattern as approval): `trace.recommendedUnitRate` is set to the true final rate and `trace.explanation` is rebuilt from the winning stage's own recorded reasoning, prefixed with the shared `deriveRateProvenance` label; the baseline's original explanation is preserved verbatim in a new `trace.baselineExplanation` field (set once, idempotent). Result: 672/672 items have `trace.recommendedUnitRate` identical to the final rate (previously divergent for every later-stage overwrite); 314 traces were reconciled to a later stage on the Kohler run.

**Residual deviation profile (the remaining 118).** Dominated by ambiguous child-row descriptions that legitimately price differently per parent context but share one master item — e.g. "End terminations" appears in Kohler itself at ₹120-₹2,200 depending on the parent cable spec, and every such row now receives the same (Kohler-sourced, plausible, but context-blind) rate. Fixing this class requires parent-hierarchy-aware item identity (using `item.parentHierarchy` in master matching/retrieval), which is a feature beyond this audit's scope; the "Ambiguous Sub-Item Description" attention flag already marks these rows for review. Of the four explicitly-named catastrophic examples from §0: Water Body flooring (₹550,000), Glass Flooring (₹45,000) and PCC (₹1,050) now reproduce their historical rates exactly; Tile Cladding Type 2 recommends ₹3,000 vs historical ₹3,500 (14.3% off — a near-variant Kohler tile-cladding rate was selected over the exact Type-2 match; correctly surfaced as Needs Review rather than silently Auto Approved, and no longer the ₹0.15 catastrophe).

**Explicitly not modified** (per the brief, verified correct against live data): `wordOverlapScore`, `numericJaccard`, the multiplicative `overallMatchScore` formula, and `getSimilarProjects`' weighting logic.

## Follow-up Fix (2026-07-24, later same day) — bug report on "Tile - Type -01 (1200mm x 1200mm)"

**Trigger.** A drawer bug report on this exact item (Row 7, Interior, `rfq_pl2g9aiph`): header "Recommended Unit Rate" showed ₹1,600, "Selected Historical Rate" and the Historical Evidence table both showed ₹3,000 (Kohler, 100%/100% item/spec similarity, marked SELECTED), and the Pricing Explanation text itself claimed "Self-validation second pass replaced a weakly-supported estimate (₹1600.00) with a better-evidenced one (₹3000.00)" - a self-contradicting drawer. The report posed two hypotheses: (a) `recommendedRate` itself is wrong (self-validation decided but failed to persist), or (b) only `recommendationTrace.recommendedUnitRate` is stale (fix 4's reconciliation missed a subfield).

**Diagnosis method.** Static reading of the persisted record alone could not distinguish the two hypotheses cleanly, so the pipeline was instrumented with per-stage `console.log`s for this item (baseline, post-`HistoricalRetrievalEngine`, post-`ProjectCalibrationEngine.runProjectCalibration`, self-validation entry/relaxed-candidate/adoption-decision, pre/post `CommercialDecisionEngine.finalizeItemDecision`) and `/recommend` was re-run live. The trace showed:

```
[baseline]         recommendedRate=3000  matchedMasterId=mstr_f8g3450s7  confidence=85  source=Basic Rate
[post-calibration]  recommendedRate=1600  calibrationApplied=true  calibrationReason="...1600...3000..." (STALE - pre-existing on the item before this run even started)
[self-validation]   reasons=["Weak historical support (<2 references)", "...46.7% deviation..."]
[self-val relaxed]  relaxedMatchScore=67 < currentMatchScore=100 -> better=false (correctly declined to act)
[pre-decision]       recommendedRate=1600  (unchanged by self-validation this run)
```

**Actual root cause - neither hypothesis (a) nor (b) as framed, but severity-equivalent to (a).** `recommendedRate` really is wrong (1600 instead of the correct 3000), but the mechanism is a third, more fundamental defect:

1. **Engineering Adjustment overrides an already-exact historical match.** `result.source` from `RecommendationEngineV2.recommendItem` is *unconditionally* `"Basic Rate"` for every item (confirmed in source: no separate exact-match branch exists), so `server.ts`'s gate `if (result.source === "Basic Rate")` before invoking `EngineeringAdjustmentEngine.computeEngineeringAdjustment` ran for every item regardless of match quality - including this one, which already had `matchedMasterId` set via an *exact* (lowercased, trimmed) description match against the Master Catalog, confidence 85, baseline rate ₹3,000 "used directly" per `RecommendationEngineV2`'s own generated text. Engineering Adjustment then built a dimensional "family" keyed on `"tile type size"` that pooled in **a Lintel** (`"Type 02 - Size of Lintel: 150mm x 150mm"`, ₹850 - an unrelated item, not a tile at all), **the known ₹0.165 corrupted vitrified-tile rate** (documented as residual data debt in this audit's Fix 2 notes - undetectable by intra-item quarantine since every sibling of that master is corrupted), and **an unrelated "Printed Tile Flooring" variant** (₹1,600, coincidentally also 1200mm) - and used that contaminated 4-item family to Area-Scale/interpolate ₹1,600, overriding the genuine ₹3,000 exact match. Self-validation's own trigger conditions ("weak support", "high deviation") were then just detecting the *symptom* of this corruption (comparing the corrupted 1600 against the correct 3000 evidence), not a separate issue.
2. **`item.calibrationApplied`/`item.calibrationReason` are never reset at the start of a run.** These two fields were left over from a *prior* run (before this session's earlier Fix 1 changed the self-validation adoption criteria) where self-validation *had* adopted a switch to ₹3,000. On the current run, self-validation correctly declined to act (`better=false` - the exact match's evidence quality, 100, beats the relaxed alternative's 67), but nothing ever clears `calibrationApplied`/`calibrationReason` when self-validation's "not adopted" branch runs, so the stale ₹1,600→₹3,000 narrative kept displaying indefinitely, describing a decision that no longer held.

**Fixes applied (server.ts, src/CommercialDecisionEngine.ts):**
1. Gated Engineering Adjustment to `result.source === "Basic Rate" && !result.matchedMasterId` - it is a fallback for the true "flat catalog guess" case (no master match at all), never a second opinion on an already-exact match, matching the block's own pre-existing comment ("the flat Basic Rate catalog guess is replaced") which the code never actually enforced.
2. `item.calibrationApplied = false; item.calibrationReason = undefined;` explicitly reset at the top of each item's per-run processing (same "explicitly clear rather than merely skip" convention already used for `installationRate` in the same loop), so these fields can never carry a narrative across runs unless a stage in *this* run actually sets them.
3. Extended `CommercialDecisionEngine.reconcileRecommendationTrace` (the Fix-4 mechanism) to also sync `trace.historicalUnitRate` to `item.marketRateStatistics.selectedRate` whenever they diverge - the same staleness class the bug report's hypothesis (b) predicted, just in a field fix 4 didn't originally cover.

**Step 3 regression check - confirms the bug report's suspicion that fix 4's original check had a gap.** Fix 4 only ever verified `recommendedRate === recommendationTrace.recommendedUnitRate`, which are written together by the same code and so trivially agree even when both are wrong (they did, at 1600, on the buggy record). Re-running the expanded check against every rate-bearing field the drawer reads:

| Check | Before (committed baseline, 672 rated items) | After fix |
|---|---|---|
| `recommendedRate` vs `decision.recommendedRate` | 0 | 0 |
| `recommendedRate` vs `recommendationTrace.recommendedUnitRate` (fix 4's original, only, check) | 0 - **passed clean on the buggy data, confirming the gap** | 0 |
| `recommendationTrace.historicalUnitRate` vs `marketRateStatistics.selectedRate` | 292 | 0 |
| `calibrationReason`'s claimed final value vs actual `recommendedRate` (the real defect signature) | **113** | 0 |

**Step 4 - scan for other instances, confirmed widespread, not a one-off.** Scanning the pre-fix committed store (`rfq_pl2g9aiph`, 672 rated items) for Engineering Adjustment applied despite a 100%/100%-similarity exact historical match already present in `marketRateStatistics.historicalEvidence`: **88 items (13%)** - e.g. "Boardroom Table (5600mm x 1800mm)", four separate glazed-door types, "Waterproofing (For Floor + Walls 600mm High)". This was a systemic pipeline defect, not specific to the reported tile item.

**Overall regression impact.** `test_historical_replay.cjs` on `rfq_pl2g9aiph`: >5% deviations **118 → 72 (21.9% → 13.4%)**, catastrophic (>90%) 31 → 29. This is the largest single-fix improvement since Fix 3 (the project-identity fix) - confirming Engineering Adjustment overriding exact matches was a materially significant, previously-undetected pricing defect, not merely a display inconsistency.

**Lesson.** A regression check that only compares two fields written by the *same* code path (`recommendedRate` and `recommendationTrace.recommendedUnitRate`, both set by the same self-validation write) can pass cleanly while both are simultaneously wrong relative to the actual evidence. The check that would have caught this - cross-referencing `calibrationReason`'s own claimed outcome against the field it claims to describe - didn't exist until this fix. When verifying "does X match Y," prefer checking X and Y against an independent third source (here, the evidence pool itself) over checking two fields that share a writer.

## Follow-up Fix 2 (2026-07-25) — "Counter Size 01-850mm" bug report: reported as two bugs, actually one root cause

**Trigger.** A correction to a prior report on Row 128 ("Counter Size 01-850mm H 750mm D 1500mm L", `rfqit_u2jxi3upk`): the source sheet shows this exact description priced at ₹55,000 in the same project/worksheet, but the drawer recommended ₹85,000, with the baseline stage citing a *different* item's ("...3290mm L") "Historical Commercial Rate" as ₹70,000 before self-validation bumped it to ₹85,000. The report was framed as two independent defects - **Bug 1**, an exact-match retrieval failure (the 1500mm item never appearing in `historicalCandidates` or `discardedEvidence`), and **Bug 2**, independent master-catalog data corruption (₹70,000 stored vs. ₹85,000 real) not caught by the existing median/MAD outlier guard. The brief explicitly asked to keep them distinct if they were.

**They are not distinct - both are downstream symptoms of a single ingestion-time defect.**

**Root cause.** `server.ts`'s master-catalog clustering step (the loop that builds `MasterBOQItem`s from raw historical BOQ rows, ~line 2288) merges a new row into an existing master when `calculateWordOverlap(rawDesc, master.standardDescription) >= systemSettings.similarityThreshold` (0.65). That function has a numeric-token guard specifically meant to stop unrelated-but-word-similar specs from merging (e.g. a "10 Sqmm" cable and a "300 Sqmm" cable) - but the guard only penalized when *fewer than half* of a description's numbers agreed (`numericJaccard < 0.5`). A multi-axis dimension callout like `"Counter Size 01-850mm H 750mm D 1500mm L"` carries **four** numeric tokens (item code "01", H "850", D "750", L "1500"/"3290"). Two rows differing *only* in the one axis that actually drives price (L: 1500 vs 3290) still agree on 3 of 4 numbers - `numericJaccard = 3/5 = 0.6` (union counts the differing pair separately) - comfortably above the old 0.5 bypass threshold, so the guard never fired and the plain word-overlap score (0.8, driven by "counter size h d l" matching) cleared the 0.65 clustering threshold. The two rows - genuinely priced ₹55,000 and ₹85,000 - were fused into one master (`mstr_uo37dadt0`, `standardDescription` = the 3290mm text, `historicalRates: [85000, 55000]`).

Everything downstream is a mechanical consequence of that single merge:
- **"Bug 1"**: `HistoricalRetrievalEngine` never saw a "1500mm L" candidate to retrieve, reject, or log, because **no such master ever existed** after ingestion - its evidence had already been absorbed as a second array entry inside the 3290mm-labeled master. There is nothing to find in `historicalCandidates`/`discardedEvidence` because the record was never split out to begin with. The two specific hypotheses raised in the bug report were checked directly and ruled out: `familyToken()` computes the identical bucket key (`"counter"`) for both descriptions (both reduce to family key `"counter size h d l"` after dimension-stripping), so bucketing does not split them; and description normalization is applied identically on the RFQ-item side and the master side, so it does not reorder or strip the H/D/L segments inconsistently between the two.
- **"Bug 2"**: the master's `basicRate`/`medianRate`/`averageRate` of ₹70,000 is exactly `(85000 + 55000) / 2` - the median/mean of the two wrongly-merged rates, not a corrupted ingested cell. There was never a wrong Excel-cell read; the "corruption" is the arithmetic footprint of Bug 1's merge. This is also *why* the existing median/MAD outlier guard (Audit 0002 Fix 2) couldn't catch it: that guard flags a rate that's an order-of-magnitude outlier *against its own master's siblings*, but ₹55,000 and ₹85,000 are each other's only siblings inside the corrupted master and are only ~1.5x apart - never eligible to look like an outlier of each other. The guard was working correctly against the (wrong) population it was given.

A secondary, related gap was found (not the cause of the reported symptom, but worth closing while investigating the same family of descriptions): `EngineeringAdjustmentEngine.extractDescriptor`'s three-axis dimension tier (`dim3DRegex`) only matches axis callouts separated by `"x"`/`"×"` (e.g. `"800mm H X 750mm D X 3110mm L"`). This project's Counter Size rows use a **space**-separated variant with no `x` (`"850mm H 750mm D 1500mm L"`), so that tier never matched; the generic Tier 4 fallback grabbed only the *first* numeric+unit token in the string (always the H value, 850mm, identical across every L variant), classifying the item as `kind: "1D"` and leaving `primaryDimension` blind to the axis that actually varies. This did not cause the reported retrieval failure (the literal-text match already ranks the true twin above any dimension variant via semantic word-overlap alone, independent of `dimensionScore`), but it is a real, general gap for any BOQ using this common axis-letter-without-`x` dimension notation.

**Fixes applied:**
1. `server.ts`'s `calculateWordOverlap` numeric guard tightened from "less than half the numbers disagree" to **any** numeric disagreement (`numericJaccard < 1`) blocking an unfiltered pass-through. Rationale: in a BOQ line-item description, a numeric token almost always encodes a spec/dimension that drives price - master-catalog clustering (identity) must never fuse two rows over a differing number; bridging genuinely-related-but-differently-sized items is `EngineeringAdjustmentEngine`'s job (a separate, explicit mechanism), not this identity step's. Applied uniformly (also affects the CPWD-catalog seeding call site, `/api/master/load-standard`, for the same reason). Retrieval-time scoring (`HistoricalRetrievalEngine.wordOverlapScore`/`numericJaccard`) was deliberately left untouched - it is supposed to stay loose to admit dimension-variant family evidence for engineering adjustment; only the *identity/clustering* guard needed tightening.
2. `src/EngineeringAdjustmentEngine.ts`'s `extractDescriptor` gained a Tier 0b three-axis regex requiring an axis letter (H/W/D/L/T) directly after each number (mandatory, since it's the only signal distinguishing a real 3-axis callout from unrelated numbers without an `x` separator to lean on), tried only when the `x`-separated Tier 0 fails. Purely additive - `primaryDimension` still resolves positionally (first number found), matching the existing `x`-separated tier's own convention, so this is a `kind` classification improvement (1D → 3D, all three axis values captured in `parameters`), not a fix to which axis becomes `primaryDimension`. **Left as known residual debt** (not attempted): dimension-based scoring/interpolation for this description family still can't discriminate on the true cost-driving axis (it locks onto whichever number appears first in text, not the one that actually varies across a family) - solving that would mean teaching the engine to identify the *varying* axis across a family's reference points, a larger change than this bug's regression required, since the reported failure is already fully explained and fixed by the clustering fix alone.
3. **Data migration** (one-time, `master_boq_store.json`): rather than replaying full ingestion (the original Excel files aren't independently available; `historical_sheets_store` holds parsed rows but not the per-master clustering decisions), a targeted repair re-evaluated every existing master with more than one occurrence against the fixed `calculateWordOverlap`: for each occurrence, re-check it against its own master's anchor description (the occurrence that originally created the master); anything that would no longer cluster is split out and re-homed (against an existing sibling master in the same domain if the fixed rule now matches one, else spun up as a new master), recomputing rate stats. Masters where every occurrence still passes the fixed rule are left byte-identical - no ID churn for anything that wasn't actually wrong. ## Follow-up Fix 3 (2026-07-25) — "Curve Single Glazed Partition" bug report: qualifier-word loss at clustering

**Trigger.** RFQ item "Curve Single Glazed Partition" (Row 8, Modular Glass Partition & Doors, `rfq_pl2g9aiph`) recommended at ₹5,500 - the rate for the flat variant "Single Glazed Partition" - while the source sheet has both as distinct line items: "Single Glazed Partition" = ₹5,500 (row 7, correct), "Curve Single Glazed Partition" = ₹12,500 (row 8, 2.27x higher - curved glazing is a materially different, pricier fabrication). The drawer's baseline stage cited its Master Catalog source as "Single Glazed Partition" - the word "Curve" was already gone before any similarity scoring ran.

**Root cause - confirmed both parts of the hypothesis, and they compound.**

**(a) Clustering merge, confirmed.** `master_boq_store.json`'s `mstr_xpbnvyuze` (`standardDescription: "Single Glazed Partition"`) held `historicalDescriptions: ["Single Glazed Partition", "Single Glazed Partition", "Curve Single Glazed Partition"]` with `historicalRates: [4500, 5500, 12500]` - all three historical rows, from two different projects (SKF Phoenix, Kohler), fused into one master. "Curve Single Glazed Partition" never existed anywhere in the catalog as its own master. Word-overlap math: `"single glazed partition"` (3 significant words) vs `"curve single glazed partition"` (4 words) share 3 - `baseScore = 3/4 = 0.75`, above the 0.65 clustering threshold. Unlike the Counter Size defect (Follow-up Fix 2), there are **zero numeric tokens** in either description, so the numeric-Jaccard guard fixed in Follow-up Fix 2 never engages here (`nums1.size===0 && nums2.size===0` skips that check entirely) - this is a genuinely separate defect class (word-qualifier loss, not numeric-dimension loss), confirming the two bug reports were right to be investigated independently even though both live in the same clustering loop.

**(b) Equivalence-gate vocabulary, also confirmed.** `isCommerciallyEquivalent`'s `DISTINGUISHING_QUALIFIERS` list (material/rating qualifiers: fire rated, toughened, galvanized, etc.) had **zero** shape/fabrication terms - no curved/curve/radius/bent/segmented, no straight/flat/flush/rectangular. Even if this function had been consulted during clustering, it would have called the pair equivalent today. But a second, more consequential finding: **`isCommerciallyEquivalent` was never called during clustering at all** - `server.ts`'s master-clustering loop (~line 2300) only ever called `calculateWordOverlap` against `systemSettings.similarityThreshold`. The function exists and is actively used at *retrieval* time (`HistoricalRetrievalEngine`'s candidate gate) and inside `EngineeringAdjustmentEngine`'s own family-reference matching - but never at the point where a master's *identity* is formed. This meant even the **already-curated, already-correct** qualifiers (fire rated, toughened, powder coated, etc.) provided **zero protection at clustering time** - confirmed empirically during the fix (see below): wiring the existing gate into clustering, with no vocabulary changes at all, immediately split a "Fire rated bulkhead partition" that had been silently merged with its unrated sibling, and a "...powder coated back box..." speaker variant merged with an unrelated mounting-clamp variant. The clustering/retrieval asymmetry - not just a missing keyword - is the deeper structural gap.

**Fixes applied:**
1. `src/EngineeringAdjustmentEngine.ts`: extended `DISTINGUISHING_QUALIFIERS` with a generic (not glass-partition-specific) fabrication/shape group: `curved, curve, radius, radiused, bent, segmented, circular, cylindrical, straight, flat, flush, rectangular`. Same curated-list convention as the existing entries, applies across every domain (furniture, glazing, cladding, lighting, partitions) that uses these terms.
2. `server.ts`: imported `isCommerciallyEquivalent` and gated the master-clustering candidate loop on it - a `master` is only considered as a merge target if `isCommerciallyEquivalent(rawDesc, master.standardDescription).equivalent`, checked *before* the word-overlap similarity comparison (so a non-equivalent-but-high-overlap master never even sets `highestSimilarity`/`bestMatch`, correctly falling through to "create new master"). Applied to both the primary ingestion clustering loop and the analogous CPWD-catalog-seeding loop (`/api/master/load-standard`) for the same reason. Retrieval-time gating (already correct, already using this function) is unchanged.
3. **Considered and deliberately not added**: a rate-consistency/price-plausibility check at clustering time (the bug report's alternative option). Unlike the Follow-up Fix 2 numeric guard - where *any* numeric disagreement is a safe, universal signal of a different physical item - a price-difference threshold at clustering time is much riskier to calibrate: the same master item legitimately spans wide natural rate variance across projects/contractors/negotiation (e.g. this audit's own documented "End terminations" case, ₹120-₹2,200 for the *same* legitimate master item - an 18x spread). A blind price-gap guard would risk re-fragmenting exactly that kind of legitimate evidence pooling. The curated-qualifier approach (deterministic, auditable, already the codebase's chosen design for this exact problem) was preferred over a second, harder-to-tune heuristic.

**Data migration.** Same targeted-repair pattern as Follow-up Fix 2 (backed up first): re-evaluated every multi-occurrence master's non-anchor occurrences against the fixed rule (`isCommerciallyEquivalent` gate, then word-overlap threshold - mirroring the real clustering decision exactly), splitting/re-homing only what no longer belongs. ## Follow-up Investigation (2026-07-25) — "Changing project cost/size doesn't move the rate": diagnosis only, no fix applied

**Trigger.** User entered a deliberately wrong project cost/size (order-of-magnitude off) via the recommend flow and observed no change in recommended rates - asked for a precise diagnosis of which of three explanations was real: (a) the fields aren't wired into the engine at all, (b) they're wired and correctly don't move exact-match rates but do move confidence/rates for everything else, or (c) they're wired into similarity/confidence but Stage-2 pricing for non-exact-match items is insensitive to shortlist changes it should react to.

**Method.** Two `/api/rfqs/rfq_pl2g9aiph/recommend` calls issued back-to-back against the live server: Run A with an empty body (falls through to the recognized historical twin's real profile - Cost ₹5,32,24,302, Size 691,250 sq ft, Type Commercial Office, City Pune, per the precedence rule from Fix 3 above), Run B immediately after with a deliberately wrong body (`projectCost: 1000000, projectSize: 1000, projectType: "Residential", city: "Chennai", buildingGrade: "Grade B"`). Full `rfq_items_store.json` snapshotted after each call; server console log (which prints the Stage-1 shortlist every run) captured for both.

**None of the three hypothesized cases is exactly right.** The actual finding is a fourth, more precise one: the fields are correctly wired all the way into Stage-1 ranking, confidence, and approval status - but the *persisted, displayed* evidence trace (`item.marketRateStatistics`, which backs the drawer's Historical Evidence table, Selected Historical Rate, and Discarded Evidence list) has its own, independent staleness bug that makes it look like nothing changed even when everything upstream did.

**Step 1 results (before/after, actual values, not just "changed y/n"):**

| Field | Run A (real Kohler twin profile) | Run B (deliberately wrong profile) | Reacted correctly? |
|---|---|---|---|
| Stage-1 shortlist (server log) | Top 5: Kohler 95.0%, COWRKS 67.1%, SKF Phoenix 63.5%, Keppel 59.4%, Nuvama 55.3% | **Top 0** - every historical project scored below the 30% shortlist floor | **Yes** - drastic, correct reaction |
| `marketRateStatistics.historicalEvidence[].projectSimilarity` (sample item: "150mm Thik AAC Block Wall") | `[{"KOHLER...", "projectSimilarity": 95}, {"SKF Phoenix", "projectSimilarity": 63}]` | **Byte-for-byte identical** to Run A, including `"projectSimilarity": 95"` - despite Run B's own server log saying zero projects were found | **No - stale** |
| `overallConfidence` / `item.decision.confidence` (same sample item) | 82 | 54 | **Yes** - correctly dropped |
| `pricingConfidence` / `historicalConfidence` (same item) | 79 / 64 | 30 / 20 | **Yes** - correctly dropped |
| `approvalStatus` (same item) | Auto Approved | Needs Review | **Yes** - correctly flipped, tracking the real confidence drop |
| `recommendedRate` (same item, has an exact `matchedMasterId`) | ₹1,750 | ₹1,750 | **Correctly invariant** - see below |

Catalog-wide (672 items): **672/672** had byte-for-byte identical `marketRateStatistics.historicalEvidence` between Run A and Run B. `overallConfidence` changed for 588/672 (the rest had no evidence in either run). `approvalStatus` flipped for 474/672. `recommendedRate` changed for 276/672.

**Step 2 - tracing the actual break point (not in `getSimilarProjects`, contrary to the a-priori suspicion).** `RecommendationEngineV2.getSimilarProjects` (the Stage-1 function) is not the problem - confirmed reacting correctly above. The break is in how its output is *carried forward for display*: `ProjectCalibrationEngine.ts:648`:
```ts
if (stats) itemMarketStats.set(item.id, stats);
itemConfidences.set(item.id, computeItemConfidenceProfile(item, stats, item.recommendationTrace?.rateSource));
```
`stats` (`selectHistoricalEvidence`'s result) is `undefined` when the shortlist-scoped evidence pool is empty (as in Run B). The confidence line is unconditional - `computeItemConfidenceProfile` handles an undefined `stats` gracefully and correctly returns a low-but-real confidence number, which is exactly why confidence/approval react correctly. The market-stats line is **guarded with no `else`** - when `stats` is falsy, nothing is written to the `itemMarketStats` Map for that item this run. Back in `server.ts` (~line 4744):
```ts
const stats = calibrationOutcome.itemMarketStats.get(item.id); // undefined this run
if (stats) {
  ...
  item.marketRateStatistics = stats;   // never runs - item.marketRateStatistics keeps whatever it was
}
```
There is no corresponding `else { item.marketRateStatistics = undefined; }`. Since `rfqItems` are persisted, mutable objects loaded once at server start and mutated in place across every `/recommend` call, `item.marketRateStatistics` from Run B was not "the previous run's value" in the trivial sense - it was confirmed (via server log correlation) to date back to a call from **two conversation turns earlier**, whose Stage-1 output (`Kohler 71.2%, SKF Phoenix 54.7%...`) doesn't match either Run A or Run B's own inputs. The field silently accumulates whatever was last successfully computed, indefinitely, until a future run happens to produce non-empty evidence again.

**Step 3 - non-exact-match item sensitivity (the (c) hypothesis), checked directly.** Of 546 items with a `matchedMasterId`, 234 had a rate change between Run A and Run B; of 126 without one, 42 changed. The unchanged ones split into two distinct, explainable groups, neither of which is the bug the user was worried about:
1. **Correctly invariant by design** - items with an exact Master Catalog match and evidence strong enough that the self-validation second pass's "is a relaxed re-estimate actually *better*" check (Root Cause D, Fix 1 above) never finds a reason to override the baseline. Confirmed on 5 sampled non-exact-match items that *do* go through the relaxed/self-validation path ("RCC Lintel", "Antistatic Raised Flooring", etc.) - their rates moved (₹2,200→₹2,171.50, ₹5,500→₹4,955, etc.) exactly as expected when the shortlist changed.
2. **A separate, pre-existing architectural characteristic, not new in this investigation**: `EngineeringAdjustmentEngine.computeEngineeringAdjustment` (16 items in this RFQ) takes `allMasterItems` - the *entire* master catalog - not `similarProjects`/`similarityByProjectName`, for its dimensional family-interpolation reference points. This was already true before today (the "two-stage retrieval" fix scoped `HistoricalRetrievalEngine` and `ProjectCalibrationEngine` to the Stage-1 shortlist, but never extended that boundary to `EngineeringAdjustmentEngine`'s own family search). Arguably defensible - a dimensional size/rate scaling relationship within one product family is plausibly project-independent - but it does mean engineering-adjusted rates are, by design or oversight, insensitive to project-profile changes. Flagged here, not fixed - a genuine open question, not a straightforward bug, and out of scope for a same-session fix given it wasn't what was reported.

**Answer to "which of the three cases is real": none, precisely.** (a) is false - fields reach `getSimilarProjects` and the engine correctly reacts (Stage-1 shortlist, confidence, approval status all move). (b) is half-true - exact-match rate invariance is real and correct - but incomplete, because it implies the *rest* of the item's displayed state moves correctly too, and specifically the evidence trace does not. (c) is also half-true for a narrow, identified subset (`EngineeringAdjustmentEngine`'s catalog-wide family search) but false as a general statement - the self-validation/`ProgressiveMatchingEngine` path *does* correctly react to shortlist changes, confirmed on live data. The actual, fourth finding: **`item.marketRateStatistics` - the field the drawer's evidence panel reads - is never cleared when a run's evidence pool comes back empty**, so a user can see an internally contradictory drawer (a rate/confidence/approval status that correctly reflects "no similar projects found" sitting next to an Evidence table that still confidently cites "KOHLER PUNE FS 16TH JUNE @ 95% project similarity" from an unrelated earlier run) - the same *class* of "drawer shows numbers that don't agree with each other" symptom that opened this entire audit (§0), now via a fourth distinct mechanism (Fix 1: ungated evidence pools; Fix 2/3: wrong clustering; this: stale display cache).

**Not fixed in this session** - diagnosis only, per the brief. The fix is narrow and localized to `server.ts`'s `if (stats) { item.marketRateStatistics = stats; }` block (~line 4744) needing an explicit `else { item.marketRateStatistics = undefined; }`, mirroring the exact "explicitly clear rather than merely skip" convention already applied to `item.calibrationApplied`/`calibrationReason` in the Follow-up Fix 1 section above - but is left for the user to schedule as a deliberate change, not bundled into a diagnostic pass.

**Lesson.** "Does the rate change" is a necessary but not sufficient test of whether project-context inputs are wired correctly - this investigation would have wrongly concluded "case (b), working as designed" if it had stopped at recommendedRate, and wrongly concluded "case (a), nothing is wired" if it had only glanced at the unchanged Evidence table. The fields that actually decide the *commercial outcome* (confidence, approval) were correct the whole time; the field that explains the outcome to a human (`marketRateStatistics`) was silently wrong. Reinforces the standing pattern in this audit (§3 Root Cause C, Fix 5, Follow-up Fix 1 lesson): a UI/explainability field and the decision it's meant to justify are written by different code paths with different staleness guarantees, and must be checked independently - agreement between them is not evidence that either one is correct.

A minor, second explainability bug, adjacent to but distinct from the main finding - noted, not fixed, per the brief's "report before making changes."

**Secondary finding (narrower, different code path, not a corruption of ingested rate data): the RFQ blueprint's *own*, separate column re-detection has a real bug on this exact split Supply/Installation/Total layout.** `generateWorkbookBlueprint`'s column detector (`server.ts` ~line 3202-3297, entirely different code from the historical-ingestion one above - this is the semantic Supply/Installation-aware detector, used only for the RFQ blueprint panel and export cell-address write-back/validation) correctly identifies `rateCellColumn = 9` (Supply Rate) and `installationRateCellColumn = 10` (Installation Rate) via its semantic keyword branches, and separately, correctly, classifies `supplyAmountColumn = 12`, `installationAmountColumn = 13`, `totalColumn = 14` (Total Amount) via its own `isAmountQualified`/`totalOnlyRegex` branches. But the legacy/generic `amountCellColumn` field - used for the panel's "Total Amount in Column: Y" text and for `writableRateCells`/export-diff cell targeting (`server.ts:5259-5264`, `5699`) - is **never set by any semantic branch on this layout** (every column 9-14 gets claimed by a *more specific* branch first) and falls through to the blind fallback `amountCellColumn = rateCellColumn + 1` (`server.ts:3295-3297`), landing on column 10 - **which is Installation Rate, not any Amount column at all**. Confirmed in the persisted RFQ blueprint (`rfq_vrne2yv5a`): FA/PA/CCTV all show `"Calculated Rate cell is in Column: 9, Total Amount in Column: 10"`. This does **not** affect any ingested historical rate (that's the separate, verified-correct path above) and this specific RFQ is a self-replay test upload unlikely to be exported for real - but the fallback logic is generically wrong for *any* split Supply/Installation/Total layout (it doesn't check whether a column is already semantically claimed before defaulting into it), so it would recur on a real RFQ with this layout, silently mislabeling the export-validation/cell-write-back target. Flagged for a future fix, not applied here, since it falls outside what was asked (this session's Step 2 trigger - "an incorrect Rate/Amount column corrupting item rates" - does not apply, as no rate data is corrupted).

**Recommendation (reported per the brief, not applied).** The confidence heuristic is not "correctly flagging genuine structural ambiguity that happened to resolve correctly" - it is measuring a genuinely different thing (sheet-type classification) than what the label and panel placement invite a reader to assume (parsing/extraction reliability), and it happens to read low for a real, common, entirely benign pattern in MEP BOQs: short discipline acronyms (FA, PA, CCTV, and by the same logic BMS, ELV, ACMV, WSD, etc. would score identically) that carry no engineering ambiguity at all. Two independent, non-exclusive options worth considering: (a) relabel the panel so it reads as sheet-classification confidence, not unqualified "Confidence," removing the implied claim about parsing correctness; (b) extend `boqKeywords` with common MEP discipline acronyms so these sheets score consistently with their full-name siblings (Plumbing) rather than looking structurally worse for having a shorter name. Left for the user to decide and schedule - not applied in this diagnostic pass.

This generalizes to any tab name by construction - nothing in the new formula reads `sheetName` at all. Under the new formula, Modular Glass Partition & Doors and Passive Networking/FLSS Works/PHE score on par with (in the latter three cases, higher than) Civil Works/Interior Works, because their actual column detection is as good or better. `classificationReason` was also updated to describe the real signal (e.g. `"Rate column matched by header text, Amount column matched by header text. 92% of sampled rows had a numeric value in the guessed Rate column."`) instead of the old static `"Matched BOQ keywords in sheet name..."` template Follow-up Investigation 2 separately flagged as misleading (§ above) - that explainability bug is fixed as a side effect of this change, since the reason text is now generated from the same real signal as the score.

**Scope check, per the standing rule for this audit (fix the mechanism, not the reported case):** the fix does not special-case any of the specific sheet names in the bug report (Civil Works, Signages, Blinds, etc.) - it changes what the "BOQ Sheets" score is computed *from*, so it holds for any future project's domain vocabulary, including domain names never seen in Kohler or Keppel.

## Follow-up Fix 5 (2026-07-27) — the ₹1,354.82 synthetic constant: confirmed manufactured by the pricing engine, not a bad evidence pick; root-caused, fixed, verified; plus two newly-traced mismatches and one new attribute-taxonomy example

**Trigger.** A second report on the ₹1,354.82 constant (previously flagged) with decisive new evidence: it now spans an entire domain (Signages: 4 of 5 items) plus recurring hits in PHE/Toilet Works/Passive Networking/FLSS Works, across the Kohler RFQ. A cell-by-cell search of all 6 historical BOQ source files (Kohler, DHL Chennai, COWRKS Chennai, SKF Phoenix, Keppel, Nuvama Hyd) for the literal value `1354.82` found **zero occurrences anywhere in any historical source data** - ruling out "a wrong project's real evidence got selected" (that would surface as some other project's actual rate, not a number absent from every source file) and confirming the number is synthesized by the recommendation/fallback logic itself, not retrieved.

### Root cause, confirmed directly

`RecommendationEngineV2.recommendItem`'s no-evidence branch (`!matchedMaster`, `src/RecommendationEngineV2.ts` ~line 134-193) seeds `basePrice = 1000` (a flat placeholder) and applies a sequential wastage → handling → installation → margin build-up via `getAdjustmentsForDomain(item.domain)`. That function (same file, was ~line 101-109):
```js
getAdjustmentsForDomain(domain: string) {
  const DOMAIN_ADJUSTMENTS = {
    [Domain.Civil]: { wastage: 0.05, handling: 0.02, installation: 0.15, margin: 0.10 },
    [Domain.Interior]: { ... }, [Domain.Electrical]: { ... }, [Domain.Mechanical]: { ... }
  };
  return DOMAIN_ADJUSTMENTS[domain] || DOMAIN_ADJUSTMENTS[Domain.Civil];   // <- the bug
}
```
`item.domain` for the overwhelming majority of real sheets is **not** one of the 4 canonical `Domain` enum strings (confirmed repeatedly in this audit and in `docs/adr/0002-structural-attribute-matching.md` §5.1: 54 distinct real domain values exist against 4 canonical ones) - "Signages," "PHE," "Passive Networking," "FLSS Works," and "Toilet Works" all fall through to `DOMAIN_ADJUSTMENTS[domain] === undefined` and silently collapse onto **the Civil stack specifically**, regardless of what trade the item actually is. The arithmetic is exact:
```
1000 × 1.05 (Civil wastage) × 1.02 (Civil handling) × 1.15 (Civil installation) × 1.10 (Civil margin) = 1354.815 → rounds to ₹1,354.82
```
This directly answers the brief's diagnostic question: **it is domain-agnostic because it is one shared computation** - every non-canonical domain's items, regardless of trade, run through the identical `DOMAIN_ADJUSTMENTS[Domain.Civil]` branch. A Signages item and a PHE item are not being priced by two different, merely-coincidentally-equal fallbacks; they are being priced by the literal same code path with the literal same inputs.

Verified against `rfq_items_store.json` (RFQ `rfq_rrakmnivq`, Kohler) before any fix: **24 items at exactly ₹1,354.82**, spanning Signages (4 of its 5 rows - "Room Signages," "Push/Pull Signages," "Way Finding Signage," "Corporate/GST Signage"; the 5th, "Brand Logo Display," was also affected, making it 5 of 5, see below), PHE (11 items - WC, wash basin, urinal, health faucet, sink, angle cocks, P-trap, cockroach trap, MS brackets), FLSS Works (5 items - pipe size, sounders, keypad, router, fire extinguisher), and Toilet Works (3 items - self-levelling, towel rail, capacity spec). **Every one of these 24 items already carried `approvalStatus: "Manual Pricing"` and `confidence: 40`** - `CommercialDecisionEngine`'s zero-evidence rule (`!matchedMasterId && !matchTier && !engineeringAdjustment?.applied && !stats`) was correctly firing. The bug was not in the approval decision - it was that `item.recommendedRate` kept the fabricated Basic-Rate-baseline number regardless, and both the UI and the export route (`server.ts:5720`, `const rateToInject = item.overriddenRate || item.recommendedRate`) read that field directly, with no gate on `approvalStatus`. `deriveApprovalDecision`'s own existing comment - *"There is nothing behind the number - it must be priced manually"* - was already an accurate diagnosis; the code just didn't act on it.

### Fixes applied (three, all needed for a complete fix)

1. **`getAdjustmentsForDomain` (`src/RecommendationEngineV2.ts`)** - removed the blind `|| DOMAIN_ADJUSTMENTS[Domain.Civil]` fallback. Added a keyword classifier (extending `server.ts`'s existing `detectDomain` civil/interior/electrical/mechanical keyword groups, plus plumbing-adjacent labels - PHE, Toilet Works, Sanitary - which `detectDomain` itself leaves unclassified) that routes a raw domain string to the nearest of the 4 real cost structures, and a distinct, clearly-blended average-of-all-4 default for genuinely unclassifiable domains, never silently mislabeled as one specific trade. This stops the *collision* - Signages now computes via the Electrical bucket (₹1,311.41), PHE/Toilet Works/Passive Networking/FLSS Works via the Mechanical bucket (₹1,258.88) - directionally correct and no longer identical to Civil's number.
2. **`CommercialDecisionEngine.finalizeItemDecision` (`src/CommercialDecisionEngine.ts`)** - the real fix for what reaches the user. When the zero-evidence rule fires, `item.recommendedRate` is now explicitly cleared to `0` **before** `reconcileRecommendationTrace` runs (not after - ordering matters, so the trace's `recommendedUnitRate`/`explanation` and the decision's `recommendedRate` never disagree, per the same "reconciled once, single writer" principle Audit 0002 fix 4 established for the trace itself). A cleared `0` already renders correctly everywhere without further changes: `RecommendationsTab.tsx:822` (`item.recommendedRate > 0 ? money(...) : "—"`) and the export injection (`item.overriddenRate || item.recommendedRate`, falsy-safe). This is the fix that matters most going forward: it stops *any* future synthetic seed value (not just the Civil-stack number fix 1 targets) from ever being presented as a real recommendation for a genuinely zero-evidence item.
3. **`shouldSkipSheet` (`server.ts:1578`, found as a direct consequence of testing fix 1/2 against a live server restart, not something the brief asked about, but confirmed serious)** - the pre-existing skip-keyword list included a bare `"sign"` substring (intended to catch signature/sign-off pages), which also matches `"Signages"`/`"Signage"`. This function runs on **every server boot** (a startup cleanup pass, `server.ts:1591`, that filters and re-persists `rfqItems`) and **during every historical-BOQ ingestion** (`server.ts:2201`). Restarting the server to test fix 1/2 immediately, and silently, deleted all 5 Signages RFQItems for this RFQ (confirmed: `rfq_items_store.json` dropped from 677 to 672 items, Signages sheet went to 0 items) - this is not a new bug introduced by this session's testing, it is a pre-existing, real, disk-persisted data-loss bug that this session's restart happened to trigger and catch in the act; it independently explains why the master catalog has **zero Signages-domain masters** (confirmed via a full-catalog search) despite Signages line items clearly existing in at least two real uploaded projects - every historical Signages worksheet has silently never been ingested. **Fixed**: replaced the bare `"sign"` keyword with `"signature"`, `"sign off"`, `"sign-off"`, `"signoff"` (the actual intended targets). **Recovered**: re-parsed `uploads/rfq_rrakmnivq.xlsx` (the original file, still on disk) via the same `BOQParserEngine.parseWorkbookForUpload` the real upload route uses, filtered to the Signages sheet, and re-appended the 5 items to `rfq_items_store.json` as fresh Pending records (their original RFQItem IDs are not recoverable and are not preserved by this repair; no other stored record was found to reference them by ID). **Not attempted in this pass**: recovering any *historical*-BOQ Signages worksheets silently skipped by the same bug across the other 5 source projects (Kohler's own historical twin, DHL Chennai, COWRKS Chennai, SKF Phoenix, Keppel, Nuvama Hyd) - this would grow the master catalog with genuinely new Signages evidence and is recommended as explicit follow-up work, distinct from this session's RFQ-side repair.

## Follow-up Fix 6 (2026-07-28) — automated cross-project self-replay regression suite, and a hard confidence floor to stop any fabricated/guessed rate reaching an item

**Trigger.** Two standing gaps, requested as independent, ship-now work separate from the Phase A/B structural-attribute redesign: (1) self-replay had only ever been checked manually, one project at a time, on request - no standing, repeatable, cross-project regression gate existed; (2) the ₹1,354.82 constant (Follow-up Fix 5), its regression to ₹0, and the Lifting Station's ₹216 match were three different symptoms of the same underlying gap - nothing enforced a hard floor on evidence quality before a rate could reach an item.

### Part 1 - `test_historical_replay.cjs` rebuilt as a fully automated, cross-project suite

The previous version read an already-uploaded RFQ's persisted state from `rfq_items_store.json` - a manual, one-project-at-a-time check requiring someone to have already re-uploaded a historical BOQ by hand. Rebuilt from scratch:

1. For every historical project (`historical_boqs_store.json`), reconstructs that project's own BOQ as a fresh in-memory `.xlsx` workbook, built directly from its ground-truth row mappings (`historical_sheets_store/mappings_<histId>.json`) - a faithful stand-in for "the user re-uploads the historical BOQ," without needing the original binary file (not retained for historical uploads).
2. Uploads it via the real `POST /api/rfqs` endpoint (exercising the actual upload/parse pipeline) and runs the real `POST /api/rfqs/:id/recommend`.
3. Joins every resulting item back to its originating mapping by exact `(sheetName, rowNum)` - unambiguous, since the script controls exactly which row each mapping landed on (no description-matching fallback needed, unlike the old version).
4. Reports per-project and combined: ground-truth-eligible items, Manual Pricing/no-rate count (**not** counted as a miss) vs. auto-populated rate count (which can be a miss), and of the auto-populated ones - within 1% (the accuracy metric), deviating >5%, catastrophic >50%, with every deviating item listed (historical rate, recommended rate, % deviation, approval status, provenance).
5. Cleans up its own test RFQs after each run (a distinctive `fileName` marker) so repeated runs never accumulate garbage in the real RFQ store.

Runnable via `npm run test:replay-all` or `node test_historical_replay.cjs [project name substring] [--keep] [--out=file.json]`.

### Part 2 - hard confidence floor: never fabricate, never guess, always flag

**Threshold calibration, from real data, not arbitrary numbers** (per the brief's explicit instruction). Pulled `marketRateStatistics.selectedMatchScore`/`historicalEvidence[].projectSimilarity` for every one of the 2,643 ground-truth items in the Part 1 baseline and compared the "good" (within-tolerance) population against the catastrophic one:

- `selectedMatchScore`: **every currently-legitimate match sits at 53 or above** (min 53, median 100). Catastrophic deviations are **not** distinguishable from good matches on this number (catastrophic median 95, same range) - confirming that most catastrophic failures in this dataset are *confidently wrong* (a matching/attribute-identity problem - Table finish top/bottom, D3-vs-D4 door, Mist Cooling Pipeline, White Goods game tables, all Phase A/B territory), not weak-evidence problems this floor is designed to catch.
- `projectSimilarity`: **constant at 95 across virtually the entire dataset** (self-replay's own signature - a project compared against itself always finds its real twin at high similarity), so it has no discriminating power in self-replay data at all. It remains conceptually essential as a defensive backstop, since it is exactly the number that cratered to 41% in the original Kohler incident (§1 above).
- The known bad cases named in the brief (Signages: zero evidence, correctly caught by the existing zero-evidence rule already; Lifting Station: currently resolves via an exact twin, `selectedMatchScore: 73`, well above any reasonable floor) did not themselves supply a "how low can real evidence go" data point - the 53/95 empirical range above did.

**Rule chosen** (`src/decisionConstants.ts`): `MIN_SELECTED_MATCH_SCORE_FOR_AUTO_RATE = 35`, `MIN_PROJECT_SIMILARITY_FOR_AUTO_RATE = 40`. Both set safely below the observed 53/95 floor of every currently-legitimate self-replay match (guaranteeing zero regression on real, working data), while `MIN_PROJECT_SIMILARITY_FOR_AUTO_RATE = 40` sits just above Stage-1's own `MIN_PROJECT_SIMILARITY_TO_SHORTLIST = 30%` shortlist floor (`src/RecommendationEngineV2.ts`) - specifically calibrated to have caught the original Kohler 41%-similarity incident (§1) had it recurred. Enforced centrally in `CommercialDecisionEngine.evaluateEvidenceSufficiency` (new, shared by `deriveApprovalDecision` and `finalizeItemDecision`) - when evidence exists but fails either floor, the item is routed to Manual Pricing with `recommendedRate` cleared to 0, identical treatment to true zero evidence, never a fallback computation of any kind.

**A self-inflicted bug, caught before shipping, worth recording as its own lesson.** The first implementation exempted any item with `item.matchedMasterId` set from the floor entirely, reasoning that an exact text match already carries its own fixed 85% confidence. This was wrong: `matchedMasterId` is written once, by the baseline stage, and is **never cleared** when a later stage (calibration/self-validation, Progressive Matching) completely replaces the rate with different, weaker evidence - discovered by deliberately lowering the floor to 60 (above the observed 53 minimum, to force a trigger) and finding **zero items flipped to Manual Pricing** where at least 6 should have. Investigation found all 6 of Kohler's `selectedMatchScore: 53` items carried `provenance: "Self-Validation / Calibration"` (i.e. calibration had already thrown away the exact match and substituted weaker evidence) while still holding a stale `matchedMasterId` from their original baseline stage - the naive check would have made the floor permanent dead code for exactly the population it exists to catch. **Fixed**: the exemption now requires `!item.calibrationApplied && !item.matchTier` in addition to `matchedMasterId` - i.e. `matchedMasterId` is only trusted when nothing downstream has actually touched the rate. Re-verified at the same forced threshold (60): exactly 6 Kohler items correctly flipped to Manual Pricing (matching the 6 independently identified via the raw data query), confirming the mechanism works, not just that it compiles. Restored to the calibrated 35/40 before the final run below.

### Step 2 - the real root cause: two compounding bugs in historical-BOQ ingestion's column parser (`server.ts`, the `POST /api/historical-boqs` row-parsing loop, ~line 2213-2280 pre-fix)

Kohler's own `HVAC` worksheet (`historical_sheets_store/hist_vsro0d05m.json`, verified directly against the raw, pre-ingestion row dump - not inferred) has a two-row merged header:
```
Row 0: ["SR. NO", "DESCRIPTION", "UNIT", "QTY", "Supply - A", null, "Installation - B"]
Row 1: [null, null, null, null, "Rate", "Amount", "Rate", "Amount"]
```
and rows like:
```
["a", "0.63 TR Compact Cassette", "Nos", 0, 30225, 0, 3255, 0]
["a", "0.63 TR- Hi-Wall type",    "Nos", 0, 19530, 0, 2325, 0]
```
i.e. a real, fully-quoted Supply Rate + Installation Rate for **every** capacity/model option Kohler's HVAC vendor priced, with `QTY = 0` for the options this specific project didn't end up purchasing (a completely standard "rate-card" BOQ convention - list every option, quantity fills in only what was actually ordered). These rows were never mangled or missing; the ingestion parser simply never captured them, for two independent reasons that compound on exactly this kind of sheet:

1. **`row[col] || ""` treats a genuine numeric `0` as blank.** `rawQtyStr = String(row[colQty] || "").trim()` - when the cell's real value is the JS number `0` (not missing, not blank - a real quoted-but-unordered quantity), `0 || ""` evaluates to `""` (0 is falsy), so `rawQtyStr` becomes empty and `qty = parseFloat("")` is `NaN`. The row-classification check `isHeaderRow = isNaN(qty) || isNaN(rate) || !rawUnit || ...` then treats the row as a hierarchy sub-header and `continue`s past it - discarding its real, already-quoted rate along with the (irrelevant) zero quantity. This is a general bug, not HVAC-specific in mechanism - it fires on *any* domain's genuinely-zero-quantity rate-card row - but HVAC equipment schedules are conventionally written exactly this way (list every capacity/model, zero out what wasn't bought) far more than Civil/Electrical/Interior sheets, so it devastates HVAC almost exclusively in practice.
2. **No combined "Total Rate" column exists on this sheet, and the naive column-header scan silently keeps only the last "rate"-labeled column it sees.** Unlike Keppel's FA/PA/CCTV/Plumbing sheets (verified correct back in Follow-up Investigation 2 - those have an explicit `TOTAL RATE (INR)` column), Kohler's HVAC sheet only has "Supply - A" / "Installation - B" as two separate group headers, each with its own "Rate" sub-header one row below. The original column-scan loop just overwrote `colRate` on every `/rate/`-matching cell it found, left-to-right, so it landed on the **Installation Rate column only** (₹3,255 for the 0.63 TR Compact Cassette row above) and silently dropped the Supply Rate (₹30,225 - ~90% of the true composite price). This affected not only the zero-quantity rows above but **already-ingested, currently-live masters**: e.g. `mstr_gni2nakq5` "1.59 TR 4-Way/Round Flow Cassette" (qty=5, a real purchased quantity) was recorded in the master catalog at ₹5,115 - the Installation Rate alone - when the real, fully-quoted composite rate (Supply ₹43,273 + Installation ₹5,115) is ₹48,388. Every downstream consumer (`MasterBOQItem.historicalRates`, `precomputeMasterItemFields`'s Supply/Installation 70/30 *display* split, all pricing/retrieval) expects `historicalRates` to already be the single, final, composite commercial rate - this bug silently fed it ~10% of the real number for every HVAC master on this sheet, not just the zero-quantity ones this investigation started from.

**Fix applied** (`server.ts`, the historical-BOQ ingestion column-detection + row-parsing block only - the RFQ-item ingestion path was checked for the same `row[col] || ""` pattern and found to share it structurally, but was left untouched since it wasn't implicated in this defect and touching it wasn't required to resolve the reported collapse):
1. Replaced the three `String(row[colX] || "")` reads (unit/qty/rate) with a null/undefined-safe helper that only falls back to `""` when the cell is genuinely absent, preserving a real `0`.
2. Extended the column-header scan to classify each `/rate/`-matching column by a "total"/"supply"/"installation" qualifier - checked both in the cell's own text and in the row directly above it (to catch exactly this 2-row merged-header convention). When an explicit Total-qualified column exists, behavior is unchanged (still wins, matching the already-correct Keppel case). When Supply and Installation are found as two distinct columns with **no** Total column, the parser now sums both into one composite rate for that row, instead of keeping only whichever one the scan happened to see last.

Both changes are general (keyed on header text/structure, not on "HVAC" or any project name) and backward-compatible with the overwhelming majority of sheets that have exactly one plain "Rate" column (untouched code path, confirmed no `splitSupplyInstallation` flag is ever set for those).

## Follow-up Fix 8 (2026-07-28, later same day) - export regression: Manual Pricing's text flag in a Rate/Amount cell broke downstream SUM/formula chains

**Trigger.** User reported that Follow-up Fix 6's export change (writing the literal text `"MANUAL PRICING REQUIRED"` into a Manual Pricing item's Rate/Amount cells) breaks every SUM/rollup formula downstream that expects a number in that column - a genuine regression in how the confidence floor's export behavior was implemented, not a request to loosen the floor itself.

**Root cause, confirmed directly against a real exported workbook's OOXML.** Fix 6's `updateCellInXml` call site (`server.ts`, the export route's per-item injection loop) only skipped writing the text flag into a cell that **itself** already carried a formula (checked via `trackFormulaAt`) - reasoning that writing a string into a formula cell is invalid type-mixing. This check was one cell too narrow: a sheet's **Rate** cell is very rarely a formula itself (it's normally a manually-entered value), but the **Amount** cell in the same row very often is (`Amount = Rate x Qty`, confirmed live on both HVAC - `<f>+E171*$D171</f>` - and PHE - a 4-formula Supply/Installation/Total/Amount cascade, `G=F+E`, `H=N(E)*N(D)`, `I=N(F)*N(D)`, `J=N(D)*N(G)`). Fix 6 correctly left the Amount formula cell itself untouched, but still wrote the TEXT flag into the (non-formula) Rate cell it depends on - so the Amount formula's own input became text, and it recalculates to `#VALUE!` on open. Any grand-total `SUM()` elsewhere in the sheet that includes that Amount cell then also returns `#VALUE!` (SUM propagates an error found in its range, unlike an ordinary text value which it would silently skip) - exactly the reported symptom, and exactly why it wasn't caught by Fix 6's own formula-cell check: that check was watching the wrong cell.

**Fix applied** (`server.ts`, the export route's `updateCellInXml`/per-item injection block; `src/types.ts`'s `WorkbookBlueprint`):
1. A Manual Pricing item's Rate/Installation Rate/Amount/Installation Amount cells now all receive a plain numeric `0` - never text. Writing a number into a formula-bearing cell is always safe (confirmed: `updateCellInXml` only ever replaces a cell's cached `<v>`, never touches an existing `<f>` tag, and every downstream formula referencing a `0` input simply computes cleanly), so the previous "skip formula cells" special-case for Manual Pricing rows is no longer needed at all - Manual Pricing rows are now written exactly like any other row, just with `0` instead of a real rate.
2. The human-readable flag moved to two places that are never read by a numeric formula: (a) the sheet's **Remarks** column, newly detected during blueprint generation (`generateWorkbookBlueprint`'s existing header-scan loop gained a `remarksColumn` branch, matching `/remarks?|notes?|comments?/i` against column header text - the same generic, structure-based detection convention already used for Rate/Amount/Supply/Installation/Total columns) - written as plain text there, since a Remarks cell is never a formula operand; and (b) a new solid-fill cell format (`addManualPricingHighlightStyle`, appends one `<fill>` + one `<xf>` to `xl/styles.xml` per export, referencing the new format's index via a `styleIndex` parameter added to `updateCellInXml`) applied to the Rate/Amount cells themselves, so the row is visually unmistakable even on sheets with no Remarks column.
3. `WorkbookBlueprint`'s `sheets[x]` type gained `remarksColumn?: number` (`src/types.ts`).

**Verification, on a real live export (`rfq_w9hckiecu`, 12 Manual Pricing items across HVAC/PHE/FLSS Works/TOILET WORKS), inspected via direct OOXML parsing of the exported file (not literally opened in Microsoft Excel - no Excel available in this environment; verified structurally that every formula's operand cells are now numeric, which is sufficient to guarantee Excel's own recalculation cannot produce `#VALUE!` from them):**
- `TOILET WORKS!G15`/`H15` (Rate/Amount, Manual Pricing row): `<c r="G15" s="914"><v>0</v></c>`, `<c r="H15" s="914"><v>0</v></c>` - numeric `0`, styled with the new highlight format (index 914, the first newly-appended `cellXfs` entry, referencing a newly-appended amber `fill` at index 15). `TOILET WORKS!I15` (this sheet's real, detected Remarks column): `<c r="I15" s="90" t="inlineStr"><is><t>MANUAL PRICING REQUIRED</t></is></c>` - plain text, original cell style preserved (no `styleIndex` was passed for this write).

## Follow-up Fix 9 (2026-07-28, later same day) - "Above Door/Glass Partition" (Kohler self-replay): confirmed the SAME already-known project-profile bug, not a new regression; item-identity gap investigated and found inconclusive, folded into ADR-0002

**Trigger.** User asked for a rigorous re-investigation of why "Above Door/Glass Partition" shows Project Similarity 41% and fails to find its own historical twin: (1) confirm whether Fix 3's twin-auto-fill is actually firing for this upload, or has regressed/has a filename-matching gap; (2) determine whether "Above Door/Glass Partition" (this RFQ's item) and "Above Door Partition" (the Master Catalog's canonical name) are the same real-world product worded differently, or a genuine material/type distinction (same class as Wet/Serving counters, Curve/flat glazing); (3) fix whichever is the actual cause.

### Step 1 - is Fix 3 regressed, or filename-pattern-limited?

**Neither.** Direct inspection of this item's persisted record (`rfqit_2j8qvi1v4`, RFQ `rfq_w9hckiecu`, "Copy of KOHLER PUNE FS 16TH JUNE") shows `marketRateStatistics.historicalEvidence[0]` already correctly identifies **"KOHLER PUNE FS 16TH JUNE"** - its own real historical twin - as the selected evidence source, with `projectSimilarity: 41`. So the twin IS being found by name; the number computed for it is just wrong. Cross-checking this RFQ's `projectContext` (cost `₹6,56,29,440`, size `15,000 sq ft`, city `Pune`, type `Commercial Space`, grade `Grade A Multi-Tenant Building`) against `req.body`'s precedence chain in `server.ts`'s `/recommend` route confirms this is **the exact same architectural bug already identified and left open in Follow-up Fix 7** (itself tracing back to the 2026-07-27 ADR-0002 §9 Q5 finding): `RecommendationsTab.tsx`'s "Configure Project Profile" modal always submits all 5 fields as an explicit request body (whether pre-filled from `projectContext` or left at hardcoded defaults), which - per the route's own documented precedence (explicit body > identified twin > `projectContext` > placeholder) - permanently outranks the twin fallback that would otherwise supply Kohler's real profile. Reproduced a third time now (previously seen on `rfq_rbil8cqwi`), on a freshly re-uploaded copy of the same file, confirming this is a reliable, every-single-re-upload defect, not a one-off or a filename-pattern edge case. **Not a regression of Fix 3's own matching logic** - confirmed by calling `/recommend` directly with an empty body on this exact RFQ: `projectSimilarity` immediately reads 95% and this item's `recommendedRate` becomes ₹3,450 (the real historical rate), Auto Approved/Needs Review rather than Manual Pricing.

### Step 2 - "Above Door/Glass Partition" vs. "Above Door Partition": same product or a genuine distinction?

Checked the raw historical source directly (`master_boq_store.json`'s `mstr_ebslegce6`, not just its canonicalized `standardDescription`): `historicalDescriptions: ["Above Door Partition", "Above Door/Glass Partition"]`, `historicalRates: [2900, 3450]`, `projects: ["FS Submission FINAL SKF Phoenix 22", "KOHLER PUNE FS 16TH JUNE"]` - the two rows were already clustered into one master at ingestion (word overlap high, no `DISTINGUISHING_QUALIFIERS` term present in only one - "glass" as a bare word is not currently in that curated list at all, unlike "double glazed"/"toughened"/etc.). Cross-referenced against `historical_sheets_store/mappings_hist_g1t37na88.json` (SKF Phoenix's own ground truth, independent of the master catalog): row 31, same worksheet ("Interior Works"), **same quantity (35 SQM)**, ₹2,900. The Kohler RFQ item is also 35 SQM, same worksheet, same subcategory ("PARTITION & ASSOCIATED WORKS"). This is inconclusive rather than a clean confirm-or-deny, reported honestly as such:
- **Evidence for "same product, author-wording variance"**: identical quantity (35 SQM) and identical sheet/subcategory across two different FlipSpaces-executed corporate fit-out projects strongly suggests the same recurring architectural detail (a partition infill above a door head, in a project that also has its own dedicated "Modular Glass Partition & Doors" domain, i.e. glass partitions are already this contractor's standard system) - "Glass" plausibly being one author's more complete description of the same standard detail, not a deliberate second product.
- **Evidence for "a real distinction"**: a glazed infill above a door frame (glass + framing/edge-sealant) is a genuinely different labor/material assembly than a solid (ply/gypsum) infill, and the rate does differ (₹2,900 vs ₹3,450, 1.19x) in the pricier-for-glass direction one would expect if it were real.
- **Why this wasn't resolved either way**: the audit's own established bar for promoting a word to a hard-gating qualifier (Follow-up Fix 3's methodology) is a price-ratio check replicated across ≥2 independent master/project pairs - this is a **single** occurrence pair, and its 1.19x ratio sits in the range this audit has previously seen on both sides (e.g. the already-confirmed-real Tuk Shop Wet-vs-Serving-counter distinction is only 1.14x; several purely-coincidental cross-project rate gaps of similar size exist elsewhere in the catalog with no material distinction behind them at all). One data point cannot clear that bar in either direction.

**Not fixed as a new hard-coded qualifier** - adding "glass" to `DISTINGUISHING_QUALIFIERS` on a single, ratio-ambiguous instance would risk exactly the over-fragmentation Follow-up Fix 3's own notes warned against, and would not be a generalizable, evidence-backed rule the way the existing shape/fabrication qualifiers are. Per the brief's own suggested path, **folded into `docs/adr/0002-structural-attribute-matching.md` as a confirmed real-world "material class, ambiguous single-instance" example** for the Phase B discovery mechanism (empirical rate-correlation across ≥2 masters/projects) to evaluate once more catalog data exists, rather than decided unilaterally here.

A separate, real mechanism was also found while investigating Step 2 (reported, not fixed - out of scope for this brief): `HistoricalRetrievalEngine` scores an RFQ item's text against the master's single canonical `standardDescription`/`precomputedSpecification` ("Above Door Partition"), not against the SPECIFIC historical occurrence text that's actually attributable to the matched project (`historicalCandidates[0]` already correctly attributes rate ₹3,450 to "KOHLER PUNE FS 16TH JUNE" specifically, yet `semantic`/`specification` still scored only 75/75 against the canonical text, rather than 100/100 against Kohler's own verbatim "Above Door/Glass Partition" occurrence, which is byte-identical to this RFQ item's own description). This is the same class of gap as the already-documented "Table finish top/bottom" and "D3/D4 door" residual debt (Follow-up Fix 5) - a downstream consequence of clustering collapsing multiple occurrences' text into one canonical description, not a new defect - noted for completeness, not actioned separately.

### Step 3 - fix applied: Step 1 (project-profile precedence), not Step 2

Per the brief, fixed the confirmed, actionable cause (Step 1) rather than the inconclusive one (Step 2, folded into the ADR instead).

**Fix** (`src/components/RecommendationsTab.tsx`): the modal now tracks, per field, whether the user actually edited it in the current modal session (`profileFieldsTouched`, reset to all-`false` every time the modal opens) - the value shown was never a reliable signal of user intent (every field always shows *some* non-empty value, either pre-filled from `projectContext` or a hardcoded default like "Gurgaon"/"Grade A", so a value alone can't distinguish "the user chose this" from "the user never touched this"). `handleProfileSubmit` now builds the `/recommend` request body from only the touched fields - an untouched field is omitted from the JSON body entirely (not sent as an empty/placeholder value), letting the server's own already-correct precedence chain (explicit body > identified twin > `projectContext` > placeholder, unchanged, Follow-up Fix 7 - "Above Door/Glass Partition"'s own §1 finding confirms it was never broken) fall through to the twin's real profile for anything the user didn't deliberately override.
